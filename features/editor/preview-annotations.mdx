Annotation mode lets you drop numbered pins on the live preview, each with a short note like "make this wider" or "wrong color here."

## Why pins beat prose

Describing a UI change in prose is hard: "the second-to-last CTA, above the fold, but only on the pricing page" is easy to mis-target. A pin points at the exact element. The agent reads geometry, not intent.

## What each pin captures

- A **numbered marker** on the preview.
- The **element** it's attached to (from the visual editor bridge).
- Your **short note**.
- Optional **priority** (nice to have, must fix).
- The **breakpoint** you were viewing when you placed it.

## Structured brief

The pins compile into a clean, numbered brief the builder reads on its next pass, so feedback lands on the exact elements you marked. The brief looks like:

```text
1. Header CTA — increase width to full row on mobile
2. Pricing card, "Pro" — swap accent to primary token
3. Footer link "Docs" — broken, should point to /docs
```

The agent runs down the list in one turn, checks each fix, and reports what shipped.

## Working with a team

- **Share a preview link with pins on.** A collaborator can drop pins too.
- **Comment threads per pin.** Discuss without losing the anchor.
- **Resolve pins** as fixes ship. Resolved pins stay on the timeline so you can audit the round.

## Offline-safe

It's all plain structured data. It works offline, and it doesn't depend on a screenshot service. Pins survive refreshes and reload with the project.
